# Module Wizard Implementation Tasks (20251210)

This plan contains a checklist of follow-up tasks, improvements, and tests for the Module Wizard dynamic organism feature introduced in the project.

## Goals
- Make Module Wizard production-ready: robust persistence, full field-type support, accessibility, and tests.
- Keep Clean Architecture: domain ports & use-cases, adapters, hooks, UI atoms/molecules, organisms.

## High-level tasks
- [ ] Domain & Adapter
  - [ ] Add or extend adapters if required for integration tests (e.g., `SQLiteRecordAdapter` integration tests).
  - [ ] Normalize DB values during mapping (already done for `enum`/`string` mapping) and add mappings for other types as needed.
  - [ ] Consider DB migration to standardize `type` values to domain enums if preferred.

- [ ] Persistence
  - [ ] Implement `CreateRecordUseCase` and `useCreateRecord` hook (done).
  - [ ] Add `getRecord` and `getRecords` use-cases if needed.
  - [ ] Add `updateRecord` if edit/update flow is required.
  - [ ] Add integration tests that create `Record` and `RecordField` in the test DB and validate recordings and joined queries.

- [ ] UI / Organism
  - [ ] Expand `ModuleWizard` organism support to more field types:
    - [ ] MULTISELECT
    - [ ] BOOLEAN
    - [ ] NUMBER (including min/max validation)
    - [ ] DATE & TIME (native pickers)
    - [ ] TEXTAREA (multiline)
  - [ ] Allow conditional fields where selection shows further inputs (e.g., `Discomfort -> note` behavior).
  - [ ] Add icons mapping (module-field `icon` field, optional) or use provided icons per value.
  - [ ] Add fallback UI for unknown types (show warning + capture via `TextField`), but produce issues in dev-only mode.

- [ ] UX & Accessibility
  - [ ] Ensure `CardWithDetails` uses radio semantics for `SELECT` fields (aria / a11y props if needed) — already in pattern; validate with tests.
  - [ ] Ensure keyboard and screen reader support for all components.
  - [ ] Add and refine animations for step transitions and selection micro-interactions.

- [ ] i18n & Content
  - [ ] Confirm the approach: fields have i18n keys in module data or default to raw text; implement fallback.
  - [ ] Decide if `values` in DB should be i18n keys or localized strings; document the decision.

- [ ] Tests
  - [ ] Unit tests
    - [ ] Hook: `useModuleWizard` (validation and step navigation)
    - [ ] Organism: Parsing and option rendering (must be robust to malformed `values`), and `onComplete` behavior
    - [ ] Mappers and adapters (e.g., `ModuleField` mapping, `Record` creation)
  - [ ] Integration tests
    - [ ] Real DB for adapter: create record and assert `RECORD_FIELD` entries are present.
  - [ ] E2E tests
    - [ ] Full dynamic registration for the CIC module
    - [ ] A11y checks in the UI flows

- [ ] Developer Tooling and Docs
  - [ ] Add documentation to `docs/architecture` and `docs/plans` explaining how the Module Wizard works and how to add new field types.
  - [ ] Add a recipe for adding new module field types and their UI implementations.
  - [ ] Add example YAML / JSON DB seeds for new field types with annotated i18n keys.

- [ ] Cleanups & Enhancements
  - [ ] Expose `valuesList` in `TModuleFieldDTO` (parsed from `values`) to avoid duplicating parsing logic in UI.
  - [ ] Move `parseFieldValues` into domain mapper if we want the fields normalized before UI consumption.
  - [ ] Centralize `ICON` mapping (domain or UI-level) — maybe new `icon` column in `module_field`.
  - [ ] Document how to build a custom `FormPage` to compose more complex field behaviors.

## Priorities (MVP -> Nice-to-have)
1. MVP: Persistence + i18n + SELECT & TEXT + basic UX polish + unit tests (HIGH)
2. Expand field types + conditional inputs + better animations (MEDIUM)
3. Integration and E2E tests + DB migration (LOW)
4. Documentation and developer recipe (LOW)

## Acceptance Criteria
- Record creation triggers DB inserts in `record` and `record_field` table and the `ModuleWizard` `onComplete` returns `fieldValues` payload.
- `SELECT` & `TEXT` types fully supported and validated on UI.
- The dynamic organism renders correctly for the CIC module and the rest of screens that use CIC flow use the organism too.
- Aligned i18n approach and `values` parsing; prefer enum-based migrations or adapter normalization.
- Accessibility & unit tests in place.

- UI/Organism: frontend/React Native engineer
- E2E tests: QA or frontend with E2E scripting

Notes & Tips
- Prefer adapter-level mapping to normalize DB strings; it minimizes UI logic.
- If multiple modules use similar flows, create `useModuleWizardAdapter` and make the organism receive mapper overrides.
- Check `src/database/migrations` for seed format and consider a migration if you change `type` format for consistency.

Priority tip: Implement adapters and `Record` persistence first so the UI can be considered end-to-end ready for QA.
